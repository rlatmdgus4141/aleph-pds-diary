# T07 인증 구현 설명서

## ① 무엇으로 붙였나
- 방식: 기존 T06 앱에 자체 세션 인증 구현. 비밀번호 해싱은 `bcryptjs 3.0.3`에 위임(bcrypt cost 12, 무작위 개별 salt).
- 계정: 사용자명(소문자 정규화, UNIQUE), 비밀번호 12자 이상·UTF-8 72바이트 이하. 72바이트를 넘으면 자르지 않고 거절.
- 브라우저: HttpOnly·Secure·SameSite=Strict·Path=/·__Host- 접두사 쿠키. 32바이트 무작위 세션 값을 사용하고 DB에는 SHA-256 digest만 저장.
- 고정 만료: 로그인 후 12시간. 로그아웃은 해당 세션을 서버에서도 삭제. 비밀번호 변경은 사용자의 모든 세션 삭제.
- 최종 T06: https://github.com/rlatmdgus4141/aleph-pds-diary/tree/f791fc84302f06b767e9b04f9a183b82265a6498
- T06 고정 커밋을 merge로 조상에 포함했다. 기존 데이터는 자동으로 최초 가입자에게 주지 않는다. 본인이 가입·로그인한 뒤 T06 전체 JSON을 빈 계정으로 가져온다. 내용·날짜를 보존하고 관계 ID를 일관되게 새 UUID로 매핑한다. 계정 소유권은 서버 세션에서 정하며 업로드 파일의 owner_id를 신뢰하지 않는다.

## ② 왜 그걸 골랐나
- 과제는 직접 가입, 비밀번호 저장 상태, 세션 폐기, 두 계정의 API 권한 거절 근거가 필요하다. 플랫폼의 ChatGPT 로그인만으로는 앱 비밀번호 저장·변경 검사를 설명할 수 없어 이 과제에 요청된 자체 계정 흐름을 구현했다.
- 검토한 대안: 플랫폼 제공 ChatGPT 로그인(SIWC). 운영 서비스라면 인증 부담을 줄일 수 있지만 이번 비밀번호 저장 실습 목표와 맞지 않아 선택하지 않았다.
- Argon2id도 검토했으나 현재 Worker 환경에서 네이티브 모듈 없이 동작하는 bcryptjs를 선택했다. bcrypt는 최신 신규 서비스의 유일한 권장안이라는 뜻이 아니다. 장기 운영 시 메모리 강도가 높은 대안과 비용을 다시 검토한다.
- bcrypt는 salt와 작업 비용을 라이브러리에 맡기며, 자체 암호 알고리즘을 만들지 않는다. 세션 및 접근 제어 연결 코드는 직접 작성했다.
- 참고: https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html , https://www.npmjs.com/package/bcryptjs

## ③ 어디를 어떻게 고쳤나
| 흐름 | 소스 위치 | 서버 처리 |
|---|---|---|
| 가입 | app/auth-panel.tsx → app/api/auth/route.ts → lib/auth-service.ts(authAction) | 원본 비밀번호 로그 없음, bcrypt 생성 후 UNIQUE 사용자명으로 저장 |
| 로그인 | 같은 경로, login 분기 | 없는 ID/잘못된 비밀번호 동일 안내·bcrypt 비교; DB 세션 생성 후 보안 쿠키 |
| 로그아웃 | AccountPanel → /api/auth → logout 분기 | 세션 digest 행 삭제 + 만료 쿠키 |
| 자료 조회 | app/page.tsx → /api/pds → session → lib/pds-service.ts(snapshot/ownedTask/ownedPlan) | 세션에서 uid 결정, plans.owner_id JOIN으로 모든 목록/단건 제한 |
| 수정·삭제 | /api/pds POST → session → mutate | 대상의 owner_id를 먼저 검증, 타인 대상이면 변경 전 404 |
| 기록 이전 | /api/import → importRecords | 빈 계정만 허용, 소유자 강제 지정, 관계 검증, 배치 저장 |
| 5일 관찰 | /api/observations → observation-service | 당일 사전 확정, 고정 예상·실행 근거 스냅샷, 2일차 후·3일차 전 규칙 변경 |
| 계정 삭제 | /api/auth delete-account | 현재 비밀번호 확인, 내 계획·연결 기록·세션·관찰 삭제, 타 계정 보존 |

GET의 임의 owner_id, user_id, 헤더 값은 소유권 결정에 쓰지 않는다. POST 생성 ID 충돌도 타인 레코드 변경으로 이어지지 않게 검사한다. 로그인 화면에는 개인 자료를 포함하지 않으며 실제 데이터 API가 인증을 강제한다. 모든 쓰기는 동일 Origin과 JSON을 요구한다.

## ④ 안 열리는 것을 확인한 기록
- `service-results.json`: 일회성 로컬 테스트 계정으로 실행한 서비스 통합 검사. 로컬 SQLite와 실제 서비스 함수를 사용했다. 브라우저나 실제 배포 HTTP 검사로 표현하지 않는다.
- 두 계정의 bcrypt 저장값이 서로 다른 결과와 동일 세션의 로그아웃 전 성공·후 거절이 들어 있다. 이 해시는 삭제한 로컬 시험 계정의 값이다.
- `http-results.json`이 함께 제공되면 배포된 API에서 실제 실행한 성공·거절 HTTP 기록이다. 실제 비밀번호와 세션 값은 저장하지 않고 `[REDACTED]`로 대체한다. 파일이 없으면 배포 HTTP 검사는 미확인이다.
- 소유권 읽기·수정·삭제를 양방향으로 확인하고, 거절 전후 상대 데이터 전체가 같은지 비교한다. 미로그인, owner_id 위조, 목록 분리, 로그아웃 후 동일 쿠키 재사용을 별도 확인한다.
- 브라우저의 클릭·비밀번호 자동완성·새로고침·모바일 레이아웃 검증은 API 검사와 별개이다. 사용자가 직접 확인한 범위만 별도 기록한다.
- 문자열 기반 비밀값 스캔은 알려진 키 형식과 생성된 검사용 원문에 대한 검사이며 모든 가능한 유출을 증명하는 것은 아니다.

## ⑤ AI와 나
- AI: 구현, DB 마이그레이션, 서버 권한 검사, 로컬·HTTP 검증 코드, 설명서 초안 작성.
- 사용자: 실제 계획과 기록 제공, 계정 생성과 비밀번호 보관, 실제 브라우저 검증, 5일 관찰과 규칙 변경의 내용 판단.
- 인증 방식은 AI가 구현 환경과 과제 요구를 검토해 선택한 안이다. 사용자가 직접 검토·동의하거나 다른 판단을 했다면 최종 제출 시 그 사실대로 보완한다. 하지 않은 판단을 했다고 기록하지 않는다.

## ⑥ 아직 못 막은 것과 한계
- MFA, 이메일 확인, 비밀번호 재설정·복구가 없다. 비밀번호를 잊으면 계정 복구가 어렵고, 비밀번호가 유출되면 추가 인증 장벽이 없다.
- 사용자명/IP별 15분 20회 제한은 있으나 분산 공격·자동 가입·대규모 DoS를 완전히 막지 못한다. bcrypt 계산 자원 소모와 DB 증가 위험이 있다. 운영용 WAF·모니터링은 추가하지 않았다.
- 입력 정규화 및 React 텍스트 렌더링을 사용하지만 전문 침투 테스트나 포괄적인 CSP 검증을 대체하지 않는다.
- 공개됐던 T06 자료는 과거 Git 이력/제출 파일/외부 복사본에 남아 있을 수 있다. T07 인증이 이미 공개된 복사본까지 비공개로 되돌리지 않는다. 기존 DB의 owner_id가 없는 T06 원본은 API에서 제외되며 새 계정에 자동 귀속되지 않는다.
- HTTP 검사와 서버 코드 스캔은 브라우저 콘솔·모든 배포 로그 전체를 검증한 것은 아니다.
- 사용자의 실제 5일 관찰은 2026-10-02~2026-10-06 완료했다. 원본은 사용자가 내보낸 plan-do-see-2026-10-06.json이며, 시험용 합성 자료와 구분한다.

## 5일 관찰 운영
- 계정 안에서 실제 당일 작업 전에 대상 할 일과 예상 시간을 고정한다. 계산 규칙은 화면/DB에 보관한다.
- 실제 날짜 정확히 5일, 1~2일차와 3~5일차를 같은 지표·단위·계산으로 비교한다. 앱은 기록 생성 시각과 기준 날짜를 서버에서 정하며 소급 날짜 입력을 받지 않는다.
- 2일차 마감 후, 3일차 시작 전에 새 규칙 하나와 이유를 저장한다. 두 앞선 날짜의 기록 ID와 변경 시각을 보존한다.
- 하루 마감은 당일에 한다. 누락은 값 0으로 꾸미지 않고 지표 null로 표시한다. 예상 대상은 미완료여도 제외하지 않는다. 실행 ID 중복은 DB UNIQUE로 방지하며, 사람이 별도 ID로 중복 입력한 것은 직접 점검한다.
- 새로고침 후 저장 확인, 전체 JSON 내보내기, 손계산 대조와 플랫폼의 구간 기록은 사용자가 실제 날짜마다 진행한다.

## 이번 실행에서 확인된 검증 상태
- 로컬 서비스 통합 검사: 최신 결과 기준 28/28 통과. 타입 검사와 Worker 빌드 통과.
- 공개 배포 API 시도: 최초 미인증 GET에서 호스팅 엣지 응답 403 / `error code: 1010`. 앱이 반환한 인증 거절로 인정하지 않음. `http-blocked-at-edge.json`에 원본 결과 보관.
- 내부 미리보기 API 시도: 최초 GET에서 연결 거절 502. `http-blocked-in-preview.json`에 원본 결과 보관.
- 두 HTTP 시도는 계정 생성 전에 중단됐으므로 테스트 계정이나 실제 관찰일을 생성하지 않았다. 배포된 앱의 실제 HTTP 보안 검증은 아직 미완료이다.
- `tests/t07-http.py`를 배포 주소에 정상 접근 가능한 환경에서 실행하면 일회성 계정 두 개로 요청·응답 근거를 만들고 종료 시 해당 계정을 삭제한다. 실계정 비밀번호는 필요하지 않으며, 결과에서 비밀번호/세션 값은 가린다.
- 사용자 보고로 가입·로그인·기존 JSON 가져오기의 정상 동작을 확인했다. 실제 5일 관찰·마감·전체 내보내기는 사용자 최종 JSON으로 확인했다. 사용자 확인을 배포 API의 양방향 보안 검사 전체 통과로 확대하지 않는다.

## 관찰 시작 선택 오류 수정
완료 처리한 할 일이 화면에서 사라진 뒤에도 이전 선택 상태가 남아 요청에 포함될 수 있었다. 이제 UI에서 진행 중·미삭제·예상 시간 존재 항목만 선택에 유지하고, 서버에서도 동일 조건을 검사한다. 시작 전 선택 개수와 예상 합계를 표시한다.
작업 시작 전 선택 오류는 당일의 미마감 관찰에 한해 취소 가능하다. 실제 작업 미시작 확인과 사유가 필요하며, 시작 이후 연결 실행 기록이 있으면 서버가 거절한다. 취소 전 관찰 전체 스냅샷·대상·예상·시작 시각·취소 시각·사유를 observation_cancellations에 보존하고 5일 집계에서 제외한다. 마감된 관찰은 취소할 수 없다. 취소 후 새 시작은 새 시각·ID로 남는다.

## 실행 시작이 관찰 확정보다 앞선 경우의 복구
`exclude-order`는 아직 마감하지 않은 당일 관찰에서만 가능하다. 서버가 관찰 대상의 당일 실행 시작 시각이 관찰 기준 고정 시각보다 앞선지 확인하며, 근거가 없는 정상 관찰·다른 계정·마감된 관찰은 거절한다. 실행 기록과 완료 상태를 변경하지 않는다. 기존 관찰 JSON과 당일 연결 실행 근거, 제외 사유·시각을 취소/제외 이력에 보존하고 5일 집계에서만 제외한다. 실제 작업을 하지 않았다고 확인할 필요가 없다. 새 관찰은 아직 시작하지 않은 다른 작업을 실제 시작 전에 확정해야 한다.
